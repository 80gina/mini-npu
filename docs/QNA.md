## Part A. 과제 목표 (구술로 설명할 6가지)

### <a id="a1"></a>A1. MAC(Multiply-Accumulate) 연산이 무엇이고, AI에서 왜 중요한가요?
**답변**
- MAC은 같은 위치의 두 값을 **곱하고(Multiply)** 그 결과를 **계속 더해(Accumulate)** 하나의 숫자로 만드는 연산입니다.
- AI가 이미지를 볼 때는 필터(기준 모양)를 이미지 위에 겹치며 이 연산을 수없이 반복합니다. 한 장의 고화질 이미지에도 수억 번의 MAC이 필요합니다.
- CPU는 일을 순서대로 하나씩 처리(직렬)하는 데 맞춰져 있어 이 반복 계산이 느립니다. 그래서 수천 개의 MAC을 한 번에 동시에(병렬) 처리하는 AI 전용 칩 NPU가 만들어졌습니다.
- 저는 이 연산을 NumPy 없이 반복문으로 직접 구현했습니다(`mac()` 함수).

### <a id="a2"></a>A2. 패턴과 필터를 곱하고 더해서 유사도(점수)를 계산하는 원리를 설명해 주세요.
**답변**
- 필터는 "찾으려는 모양"을 0과 1로 적어 둔 판입니다. 십자가 필터는 `0 1 0 / 1 1 1 / 0 1 0`입니다.
- 패턴과 필터를 겹쳐 같은 칸끼리 곱하면, **둘 다 1인 칸만 1**이 되고 나머지는 0입니다. 이것을 모두 더하면 "겹치는 칸의 개수"가 점수가 됩니다.
- **높은 MAC 점수는 필터와 입력이 더 많이 일치한다(더 닮았다)는 뜻**이고, 점수가 더 높은 쪽으로 판정합니다.
- 예시: 십자가 패턴 × 십자가 필터 = **5점**(5칸이 모두 일치), 십자가 패턴 × X 필터 = **1점**(가운데 1칸만 겹침). 점수가 더 큰 쪽이 더 닮은 모양입니다.
- 증빙: 모드 1 화면(`docs/screenshots/M6_mode1_result.png`), 생성 패턴 결과(7x7에서 Cross 13.0 대 X 1.0).

**꼬리 질문**: 점수가 같으면요? → 판정 불가(모드 2는 UNDECIDED)로 처리합니다. (A4 참고)

### <a id="a3"></a>A3. data.json의 "키 규칙/라벨 규칙"을 해석하고, 라벨을 정규화하는 이유를 설명해 주세요.
**답변**
- **키 규칙:** 필터는 `size_5`, `size_13`, `size_25`처럼 크기별 키이고, 패턴은 `size_{N}_{idx}` 형태입니다. 패턴 키에서 N을 뽑아(`size_13_2` → 13) 같은 크기의 필터를 골라 씁니다.
- **라벨 규칙:** 필터 키는 `cross`/`x`, 정답(expected)은 `+`/`x` 처럼 **표기가 제각각**입니다. 파일마다 `Cross`와 `cross`가 섞이기도 합니다.
- **정규화 이유:** 표기가 다르면 같은 뜻인데도 "다르다"고 비교됩니다. 그래서 프로그램 안에서는 표준 라벨 `Cross`, `X` 두 가지로 통일(`+`·`cross`→Cross, `x`→X)하고, 출력과 PASS/FAIL 비교를 모두 표준 라벨로 합니다.
- **함수로 분리한 이유 4가지(README 2장):** ① 중앙집중화(필터 키·expected·비교가 같은 규칙) ② 재사용성(필터 로드와 패턴 분석 두 곳) ③ 테스트 용이성(입출력이 단순) ④ 확장 용이성(`LABEL_ALIASES` 딕셔너리에 한 줄만 추가).
- **지원 표기:** `+`, `cross`, `Cross`(대소문자·앞뒤 공백 무시)는 Cross, `x`, `X`는 X입니다. `PLUS`, `✚` 같은 변형은 **지원하지 않으며** 8-3 체크리스트로 추가합니다.
- 정규화가 하는 두 번째 일은 **잘못된 데이터 찾기**입니다. 알 수 없는 값(`?`)은 "라벨 오류"로 기록됩니다. **과제 제공 `data.json`에는 이런 값이 없고**(`x`, `+`뿐) 이 경로는 시연용 데이터(`data_failure_demo.json`)의 `size_5_3`으로 확인합니다.

### <a id="a4"></a>A4. 부동소수점 오차가 판정에 어떤 영향을 주는지, 왜 허용오차(epsilon) 비교가 필요한가요?
**답변**
- 컴퓨터는 소수를 2진수로 저장하므로 `0.1+0.2+0.3`이 더하는 순서에 따라 `0.6000000000000001` 또는 `0.6`이 됩니다.
- 사람 눈에는 같은 점수인데, `>` 또는 `==`로 단순 비교하면 아주 작은 차이(약 `1.11e-16`) 때문에 Cross가 이긴 것처럼 잘못 판정합니다.
- 그래서 `abs(a - b) < 1e-9`이면 **동점**으로 보고 UNDECIDED로 처리하는 허용오차 정책을 썼습니다.
- **1e-9을 고른 실험적 근거:** ① 제공 `data.json`에서 **동점으로 봐야 하는 케이스의 점수 차이는 1.11e-16, 2.66e-15, 1.78e-15**이고 **분명히 다른 케이스의 차이는 최소 8.8**입니다. 두 집단이 약 10^15배 떨어져 있습니다. ② 소수 0.1 단위 625개를 반대 순서로 더하는 실험을 2만 번 했을 때 **순서 때문에 생긴 최대 오차는 1.14e-12** 였습니다. ③ 그래서 1e-9은 실제 오차보다 약 **1,000배 크고**, 진짜 점수 차이(8.8 이상)보다 **약 10억 배 작아서** 오차만 걸러냅니다.
- **한계도 알고 있습니다(2차 보완):** 부동소수점 오차는 값이 클수록 커집니다. 625개를 반대 순서로 더하는 실험에서 값 범위 0~1은 최대 오차 약 1e-12(OK), **0~1000은 약 1.2e-9로 EPSILON보다 커지고**, 0~1,000,000은 약 1e-6입니다. 그래서 0과 1 데이터에서는 1e-9이 충분하지만 **값 범위가 커지면 EPSILON을 키우거나 상대 오차(`math.isclose`의 `rel_tol`)로 바꿔야 합니다.**
- **실제 사례(`size_5_1`):** X 패턴은 1이 9칸, X 필터는 칸마다 0.1이라 수학으로는 `0.1×9 = 0.9`이고 Cross 필터의 가운데 값도 0.9라 **두 점수가 정확히 같아야** 합니다. 그런데 컴퓨터는 Cross 0.9, X **0.8999999999999999**를 내서(차이 1.11e-16) 단순 비교하면 Cross가 이깁니다(정답은 X). 허용오차 규칙으로 UNDECIDED가 되고 expected와 달라 FAIL이 됩니다. 이 FAIL은 **의도된 정상 동작**이고, 오차 때문에 엉뚱한 판정이 나오는 것보다 "판정 불가"라고 알려 주는 편이 정직합니다.

### <a id="a5"></a>A5. 크기별 연산 시간을 측정하고, 시간 복잡도 O(N²)를 근거와 함께 설명해 주세요.
**답변**
- 크기별로 MAC을 **10번 반복**해 `time.perf_counter()`로 평균을 냈고, 입출력 시간은 제외했습니다.
- N×N 칸을 한 번씩 곱하므로 연산 횟수는 **N²**입니다.

| 크기 | 평균 시간(ms) | 연산 횟수 |
|---|---|---|
| 3x3 | 0.004 | 9 |
| 5x5 | 0.010 | 25 |
| 13x13 | 0.042 | 169 |
| 25x25 | 0.149 | 625 |

- 5x5 → 25x25는 크기가 5배, 연산은 25배(25→625)입니다. 시간은 약 15배 늘었습니다.
- 25배가 아닌 이유: 작은 크기에서는 함수 호출 같은 **고정 비용**이 시간의 큰 부분을 차지하기 때문입니다. 그래서 한 칸당 시간(µs)은 큰 크기에서 약 0.24로 안정됩니다.
- 결론: 시간 복잡도는 O(N²)입니다. N을 k배 하면 연산은 (kN)² = k²·N², 즉 **k²배**입니다. 예: N=5(25회) → N=10(100회, 4배) → N=25(625회, 25배) → N=100(10,000회, 400배).
- **측정 경계:** `time.perf_counter()`로 `mac()` 호출 직전과 직후만 쟀고, 입력·파일 읽기·출력·패턴 생성은 제외했습니다.
- **표 읽는 법:** `회당(µs)` = 평균 시간(ms) × 1000 ÷ N².
- **측정 환경과 편차(2차 보완):** 성능 표 위에 `측정 환경: Python 3.14.7, Windows ARM64, 반복 10회(워밍업 1회 제외)`가 출력됩니다. 첫 호출은 준비 비용 때문에 느려서 **워밍업 1회를 버리고**, 7번 재측정한 표준편차를 README에 적었습니다(25x25: 평균 0.147ms, 표준편차 0.013). 작은 크기는 값이 너무 작아 상대 편차가 큽니다.
- **예상 증가율:** 25x25를 1배로 N=100은 16배, N=200은 64배, N=1000은 1600배입니다. 칸당 0.15~0.24µs를 가정한 예상 시간(N=1000은 150~240ms)이 실측(187ms)과 맞았습니다. **크기를 2배로 하면 시간은 약 4배**입니다.

**꼬리 질문**: 측정값이 실행마다 다른 이유? → 컴퓨터 상태에 따라 달라지고 10회 평균이라 흔들립니다. 하지만 연산 횟수 N²는 항상 같습니다.

### <a id="a6"></a>A6. 실패 케이스를 "데이터/스키마 문제 vs 로직 문제 vs 수치 비교 문제"로 나누어 진단·개선해 주세요.
**답변**

| 케이스 | Cross / X 점수 | 결과 | 분류 |
|---|---|---|---|
| size_5_1 | 0.9 / 0.8999999999999999 | 동점 → FAIL | **수치 비교** |
| size_13_2 | 7.499999999999997 / 7.5 | 동점 → FAIL | **수치 비교** |
| size_25_1 | 4.9 / 4.899999999999999 | 동점 → FAIL | **수치 비교** |
| size_5_2, size_13_1, size_25_2 | 점수 차이 8.8 이상 | PASS | - |
| (없음) | - | - | **데이터·스키마 0건, 로직 0건** |

- **실패 3건은 모두 같은 원인(수치 비교)입니다.** 세 케이스는 수학적으로는 두 점수가 정확히 같도록 만들어진 데이터라, 소수를 2진수로 저장하는 오차(차이 1e-16~1e-15)가 판정을 좌우합니다. 허용오차 규칙이 없으면 **오차가 어느 쪽이 이길지 정합니다.**
- 데이터·스키마 문제는 **제공 데이터에는 없습니다.** 그래서 라벨 오류와 크기 불일치는 일부러 잘못 만든 시연용 데이터(`data_failure_demo.json`, 총 9·통과 6·실패 3)로 따로 확인했습니다. 이 경로도 프로그램이 멈추지 않고 그 케이스만 FAIL로 처리합니다.
- 진단 순서: ① 메시지에서 어떤 종류인지 읽는다 → ② 점수를 직접 출력해 값이 같은지 본다(수치) → ③ 입력 데이터의 키·크기·라벨을 본다(데이터) → ④ 그래도 다르면 계산 코드를 본다(로직).
- 로직 문제가 없다고 판단한 근거: 정상 케이스 3개는 점수 차이가 분명했고 expected와 일치했습니다. 특히 `size_13_1`은 X 점수에 `14.700000000000008`처럼 오차가 끼어도 Cross 0.3과 차이가 커서 정확히 X로 판정됩니다. **오차가 문제가 되는 것은 두 점수가 거의 같을 때뿐입니다.**
- **한 줄 표준 키 요약(2차 보완):** `요약: total=6 pass=3 fail=3 fail_label=0 fail_size=0 fail_tie=3 fail_schema=0 fail_logic=0 failed_filters=0`가 출력되어 기계가 읽기 쉽고, 로드 실패 필터가 있으면 `로드 실패 필터: size_13`처럼 따로 표시됩니다. 동점 사유는 항상 `동점(UNDECIDED):`로 시작합니다. 필터가 없으면 `스키마 오류: size_N 필터가 data.json에 없음`으로 FAIL입니다.
- 콘솔 결과 요약에는 **실패 유형별 개수**(동점 3건)가 출력되고, README에는 한 줄 요약 표(total 6, pass 3, fail 3, fail_tie 3)가 있습니다. 동점은 expected와 상관없이 FAIL로 집계됩니다.
- 프로그램은 어떤 실패에도 **멈추지 않고** 케이스 단위로 FAIL 처리하고 계속 진행합니다.

## Part B. 기능 요구 사항 점검 질문

### <a id="b1"></a>B1. 데이터 구조는 어떻게 구현했나요?
- `Grid` 클래스가 N×N 2차원 배열을 담고, `get(i, j)`로 읽고 `set(i, j, value)`로 저장합니다. 3x3, 5x5, 13x13, 25x25 모두 처리하며, 정사각형이 아니거나 숫자가 아니면 `ValueError`를 냅니다.

### <a id="b2"></a>B2. 모드 1(사용자 입력)의 입력 검증은 어떻게 했나요?
- 한 줄씩 공백으로 구분해 입력받고, **열 개수가 다르거나 숫자가 아니거나 빈 줄이면** "입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요."를 출력하고 **그 줄만 다시** 입력받습니다. Ctrl+C·EOF도 안전하게 종료합니다(`M7` 화면).
- **탭, 여러 칸 공백, 앞뒤 공백도 허용**합니다(`split()`). 주의: `010`처럼 붙여 쓰면 숫자 10 하나로 읽혀 거절됩니다. `0 1 0`으로 써야 합니다. 🧪 테스트로 확인했습니다.

### <a id="b3"></a>B3. 모드 2는 크기 불일치·스키마 오류에도 멈추지 않나요?
- 네. 파일이 없거나 JSON이 깨져도 안내만 하고 종료하며, 케이스 하나가 잘못돼도 그 케이스만 FAIL로 표시하고 나머지를 계속 처리합니다. 요약에서 총 9, 통과 6, 실패 3으로 일치합니다.

- **제공 데이터에는 이런 오류가 없어서**(6개 모두 형식이 맞음), 잘못된 데이터에도 멈추지 않는지는 시연용 `data_failure_demo.json`(라벨 오류, 크기 불일치 포함)으로 따로 확인했습니다. `MINI_NPU_DATA` 환경 변수로 그 파일을 지정해 실행할 수 있습니다.
- **스키마와 정책(README 1-2):** `filters`의 `size_숫자` 형식이 아닌 키는 **건너뛰고**, 필터 오류는 그 크기의 패턴을 모두 FAIL로, 패턴 키·`input`·`expected` 문제는 그 케이스만 FAIL로 처리합니다. 파일이 없거나 JSON이 깨지면 안내 후 종료합니다.

### <a id="b4"></a>B4. 판정과 PASS/FAIL 규칙은?
- **모드별 동점 처리 차이:** 모드 1은 정답이 없는 사용자 비교라 `판정 불가`만 표시하고, 모드 2는 자동 채점이라 `UNDECIDED`를 FAIL로 집계합니다.
- 모드 1: 점수 비교 후 A/B, 동점이면 "판정 불가". 모드 2: Cross/X/UNDECIDED로 판정하고 expected(정규화됨)와 같으면 PASS, 다르면 FAIL입니다. 동점은 expected와 상관없이 FAIL입니다.

### <a id="b5"></a>B5. 결과 리포트(콘솔·README)에는 무엇을 담았나요?
- 콘솔: 총 테스트·통과·실패 수와 실패 케이스(식별자+사유). README: 결과 리포트 섹션에 실패 원인 분석 12줄과 O(N²) 분석, 실행 방법·구현 요약·재현성을 담았습니다.

## Part D. 보너스 질문

### <a id="d1"></a>D1. 패턴 생성기를 어떻게 만들었나요?
- `make_cross(n)`은 가운데 행·열을 1로, `make_x(n)`은 두 대각선을 1로 채웁니다. 모드 3에서 N(3~25)을 입력하면 두 패턴을 만들고 서로를 필터로 삼아 판정(7x7: Cross 13.0 대 X 1.0)하며, 성능 분석에도 재사용합니다.

### <a id="d2"></a>D2. 1차원 배열로 바꾸면 왜 빨라지나요?
- 2차원 배열을 길이 N²의 1차원 리스트로 펴서(`flatten`) `get(i, j)` 호출 없이 인덱스 하나로 접근합니다. 같은 입력·같은 10회 반복에서 약 **1.8~4.7배** 빨랐고 점수는 일치했습니다.
- **큰 N의 메모리:** 격자 하나가 칸당 약 8바이트 × N²입니다. N=1000이면 7.7MB(패턴+필터 약 16MB), N=10,000이면 약 1.6GB입니다. 측정에서 N=1000일 때 2D 172ms, 1D 59ms(약 2.9배)였습니다. 다음 최적화 순서는 ① 1차원(구현함) ② 0/1을 `bytearray`로 ③ 1인 칸만 더하기(희소) ④ `multiprocessing`(표준 라이브러리 범위 밖이라 미구현)입니다.
- 그러나 연산 횟수는 N²로 같아서 **복잡도는 O(N²) 그대로**이고, 줄어든 것은 한 칸당 상수 시간입니다. 배열을 펴는 시간은 비교에서 제외했고, 10회 평균이라 배율은 실행마다 조금 흔들립니다.

## Part E. 평가 피드백 후 추가 예상 질문

### <a id="e1"></a>E1. CPU와 NPU의 병목은 각각 무엇인가요?
- 답: CPU는 소수의 강한 코어가 **직렬**로 처리해서 **연산 병렬성이 부족**하다는 것이 병목입니다. 이 프로그램의 이중 반복문이 그 예입니다. NPU는 수천 개의 MAC 유닛이 **동시에** 계산하기 때문에 연산은 빠르지만 필터와 입력 값을 메모리에서 가져오는 **메모리 대역폭이 병목**이 됩니다. 그래서 칩 안 버퍼에 값을 재사용하고 int8 같은 낮은 정밀도를 씁니다. 한 줄로: **CPU는 계산 개수가, NPU는 데이터 이동 속도가 병목**입니다.
- **계산 예시(가정 값):** NPU가 초당 1조 번(1 TMAC/s) 계산하고 MAC마다 1바이트 값 2개를 읽으면 초당 2 TB가 필요한데, 메모리가 초당 50 GB면 **약 40배 부족**해서 연산 유닛이 기다립니다. 그래서 칩 안 버퍼에 필터를 재사용합니다.
- **이 프로그램의 작은 증거:** 곱셈 횟수는 같은데 `get()` 호출을 없앤 `mac_flat`이 약 2~3배 빨랐다는 것은 **데이터에 접근하는 비용이 시간을 좌우한다**는 뜻입니다.

### <a id="e2"></a>E2. 새 라벨(예: `PLUS`)을 지원하려면?
- 답: 5단계입니다. ① `LABEL_ALIASES`에 한 줄 추가 ② `data.json` 표기 확인(표준 라벨은 그대로) ③ `LabelTests`에 시험 추가 ④ `python test_mini_npu.py`와 모드 2를 돌려 **총 6·통과 3·실패 3(동점)이 그대로인지** 확인 ⑤ README의 지원 목록 갱신. 이 절차 덕분에 정규화를 함수 하나로 모아 둔 이유를 설명할 수 있습니다.

### <a id="e3"></a>E3. 자동 테스트는 무엇을 검증하나요?
- 답: `unittest` **31개**입니다(1차 보완 때 16개, 2차에서 12개, 데이터 정정에서 3개 추가). 라벨 정규화(3), MAC(4: 문서 예시 5점·1점, 크기 불일치, 1D와 2D 일치, 생성 패턴 판정), 동점(3), 입력(3: 탭·다중 공백, 재입력, 중단), 모드 2(3: 총 9·통과 6·실패 3, 유형별 개수, 연산 횟수 N²), **EPSILON 경계(4: 0.99e-9는 동점, 정확히 1e-9와 1.01e-9는 동점 아님)**, **alias 안전성(3)**, **보고서 형식(5: 동점 접두사, 표준 키 한 줄, 필터 없음 FAIL 등)**입니다.

### <a id="e4"></a>E4. 모드 1과 모드 2의 동점 처리는 왜 다르나요?
- 답: 모드 1은 사용자가 A와 B를 비교하는 용도라 정답이 없어서 `판정 불가`로 알려 주기만 하고, 모드 2는 자동 채점이라 PASS/FAIL이 필요해서 동점(UNDECIDED)을 expected와 상관없이 FAIL로 집계합니다.

### <a id="e5"></a>E5. 보너스의 `mac_flat`이 빠른 진짜 이유는?
- 답: 연산 횟수가 줄어서가 아니라 **칸마다 `get(i, j)` 메서드를 부르는 호출 비용과 이중 반복문 오버헤드가 사라져서**입니다. 그래서 O(N²)는 그대로이고 상수만 줄었습니다.

### <a id="e6"></a>E6. EPSILON 1e-9이 항상 맞나요? 값이 커지면?
- 답: 아닙니다. 부동소수점 오차는 값이 클수록 커집니다. 값 범위별 실험에서 0~1은 최대 오차 1e-12라 1e-9이 충분하지만, 0~1000은 1.2e-9로 **EPSILON보다 오차가 커서 부족**하고 0~1,000,000은 1e-6입니다. 값 범위가 커지면 EPSILON을 키우거나 `math.isclose(a, b, rel_tol=1e-9)`처럼 값 크기에 비례하는 **상대 오차**를 씁니다. 이 과제는 0과 1 데이터라 1e-9을 그대로 썼습니다.

### <a id="e7"></a>E7. 성능 측정의 편차는 어떻게 다뤘나요?
- 답: 첫 호출이 느린 영향을 막으려고 **워밍업 1회를 버리고**, 크기당 10번 평균을 냈습니다. 측정 환경(Python 버전, OS, 반복 횟수)을 콘솔과 README에 함께 적었고, 7번 재측정해 표준편차(25x25는 0.013ms)를 표로 보였습니다. 더 안정된 비교가 필요하면 반복을 늘리거나 최소값을 씁니다.

### <a id="e8"></a>E8. 희소(1인 칸만 계산) 방식의 이점과 단점은?
- 답: 십자가·X 필터는 대부분 0이라 1인 칸의 위치만 모아 그 칸만 곱하면 **계산과 메모리를 크게 줄입니다.** 대신 위치 목록을 따로 만들어야 하고, 값이 대부분 0이 아닌 밀집 데이터에서는 오히려 느려집니다.

### <a id="e9"></a>E9. 점수를 비율로 해석할 수 있나요?
- 답: 네. `MAC ÷ 필터의 1의 개수`로 0~1 비율을 만들면 크기가 다른 케이스를 비교할 수 있습니다(십자가 필터 5÷5=1.0, X 필터 1÷5=0.2). 판정은 원점수로 하고 비율은 해석용 제안이며 구현하지는 않았습니다.

### <a id="e10"></a>E10. 데이터가 잘못되었던 적이 있나요? 어떻게 처리했나요?
- 답: 있습니다. 처음에는 과제가 제공한 `data.json`이 아니라 **제가 직접 만든 데이터(9개)** 로 분석하고 결과 리포트를 썼습니다. 제공 데이터를 확인하니 필터 값(0.9, 0.1, 7.5 같은 소수 가중치), 패턴 개수(6개), 기대 결과가 모두 달랐습니다. 그래서 ① 제공 데이터로 교체하고 ② 결과를 총 6·통과 3·실패 3(모두 동점)으로 다시 계산하고 ③ README 결과 분석을 다시 썼으며 ④ 제가 만든 9개 데이터는 잘못된 데이터 처리를 시연하는 `data_failure_demo.json`으로 보존했습니다. 11장 "데이터 정정"에 전후 비교표를 남겼습니다. **교훈:** 요구사항에 데이터가 제공되면 처음부터 그 파일을 기준으로 시작하고, 내 데이터는 보조 시험용으로만 씁니다.

## 마지막 점검: 한 문장 요약
"MAC으로 패턴과 필터의 닮은 정도를 점수로 만들고, 라벨 정규화와 허용오차로 데이터·수치 문제를 걸러 멈추지 않게 만들었으며, 연산 횟수 N²와 실제 측정으로 O(N²)를 확인했습니다."
